# Часть 2. Проект внешней обработки

Начинай, когда в `setup-log.md` есть строка `## Часть 1 — готово`. Путь из строки `Путь: …` там же: шаги 2, 4 и 6 зависят от него. Задачу человека бери из раздела `## Задача` журнала. Шаги совпадают с шагами статьи «Как подключить ИИ-агента к разработке 1С: по шагам». Каждый шаг кончается условием «Готово, когда». Не переходи к следующему, пока условие не выполнено.

### Шаг 1. Окружение

Окружение проверено в части 1. Перечитай итог в `setup-log.md` и ещё раз запусти `inventory.ps1`: человек мог что-то поменять.

Настройки набора — файл `settings.json` в корне (заполнен в части 1, шаг 1.1):

| Ключ | Что это | Обязателен |
|---|---|---|
| `v8Exe` | путь к `1cv8.exe` нужной платформы | да |
| `v8User` | пользователь базы | да |
| `v8Password` | его пароль, вписывает человек | если пароль есть |
| `baseCopy` | каталог файловой копии базы (не рабочей и не эталонной), в нём `1Cv8.1CD` | да |
| `buildBase` | база для выгрузки и сборки, если не та же копия; конфигурация та же | нет |
| `bslLsExe` | путь к BSL Language Server (`.exe` или `.jar`; для `.jar` нужна `java`) | в пути «Свои инструменты» |
| `testTimeoutMin` | предел на прогон тестов, минут (по умолчанию 10) | нет |
| `testStartMin` | сколько минут ждать, пока клиент дойдёт до тестов (по умолчанию 3) | нет |

**Готово, когда** в описи все обязательные строки ЕСТЬ, а `git config user.name` и `git config user.email` не пустые. Если чего-то нет — вернись к части 1.

### Шаг 2. Выгрузка и git

**2.1. Выгрузка обработки в файлы.** Агент не читает конфигурацию внутри базы, зато хорошо читает текст. Если человек положил в папку файл `*.epf`:

```
pwsh -NoProfile -ExecutionPolicy Bypass -File .\dump.ps1 -Epf .\<имя>.epf
```

**Готово, когда** код 0, есть `src\Обработка.xml` и рядом папка `src\Обработка\`. Имя корневого файла всегда `Обработка.xml`: на это имя рассчитаны `build.ps1` и `test.ps1`. Имя объекта внутри в путях «Свои инструменты» и «Своя связка» — любое. **В пути «Unica» объект должен называться `Обработка`:** Unica читает внешнюю обработку, только когда имя объекта совпадает с именем файла. У новой обработки так и назови; у выгруженной с другим именем переименование меняет и типы в формах — спроси человека.

Если `.epf` нет и нужна новая обработка — см. «Новая обработка без файла» ниже.

**2.2. git.** `git init`, `git add -A`, первый коммит.
**Готово, когда** `git log --oneline` показывает один коммит, а `git status --short` пуст (артефакты сборки и тестов закрыты `.gitignore`). *Почему:* каждая правка видна в `git diff`, а плохую можно откатить одной командой.

Предупреждения «LF will be replaced by CRLF» — не ошибка: так git на Windows сообщает о концах строк. Продолжай.

#### Новая обработка без файла

1. Узнай формат выгрузки для этой платформы. Выгрузка YAxUnit уже есть с части 1 (`tmp\yaxunit`); если нет — `.\dump.ps1 -Extension YAXUNIT -To tmp\yaxunit`. Формат — атрибут `version` корневого элемента в `tmp\yaxunit\Configuration.xml`. Если расширение называется иначе или его нет — спроси человека.
2. Корневой файл `src\Обработка.xml` сделай из шаблона `scripts\ExternalDataProcessor.xml` — в любом пути. Навык Unica `epf-init` готового XML не даёт (прогон 08.11), только порядок работы. Подставь в шаблоне `{{ВЕРСИЯ}}` из шага 1, `{{ИМЯ}}` — имя объекта (идентификатор, без пробелов; в пути «Unica» — `Обработка`), `{{СИНОНИМ}}` — название для пользователя, а `{{GUID-1}}`…`{{GUID-4}}` — четыре разных новых идентификатора (`[guid]::NewGuid()`). Остальное не меняй: `ClassId` — это тип объекта. Шаблон выгружен платформой 8.3.27 (формат 2.20); на другой платформе сверь шапку `MetaDataObject` с `tmp\yaxunit\Configuration.xml`. Модуль объекта — `src\Обработка\Ext\ObjectModule.bsl`.
3. `build.ps1`. **Готово, когда** `Собрано: out\Обработка.epf`, код 0. Эта сборка закрывает и шаг 5.
4. Если две сборки подряд не прошли — не перебирай дальше. Попроси человека: «Создайте в конфигураторе пустую внешнюю обработку (Файл → Новый → Внешняя обработка) и сохраните в эту папку». Потом выгрузи её по 2.1.

*Почему формат важен:* формат выгрузки привязан к версии платформы, и выгрузку одной версии другая может не прочитать. Выгружай и собирай одной платформой.

### Шаг 3. Правила

Правила — `AGENTS.md`. `CLAUDE.md` в корне ссылается на него, другие агентские системы читают `AGENTS.md` сами.
**Готово, когда** `AGENTS.md` лежит в корне. Ничего не делай.

### Шаг 4. Проверка кода до запуска базы

Самая дешёвая проверка: секунды, без запуска 1С и без изменения данных. Чем проверять — по пути из части 1.

**Путь «Свои инструменты».**

```
pwsh -NoProfile -ExecutionPolicy Bypass -File .\lint.ps1
```

Запиши число из строки `Замечаний: N` в файл `lint-baseline.txt` (только число) и закоммить. *Почему:* на чужом коде замечаний бывают сотни; начинать со всех правил сразу не нужно, но и новых замечаний добавлять нельзя.

**Готово, когда** `lint-baseline.txt` с числом закоммичен, а повторный `lint.ps1` даёт код 0.

**Стандарт за каждым новым замечанием.** На каждое новое замечание анализатора назови человеку код диагностики и стандарт разработки 1С за ним и правь по стандарту, а не так, чтобы замечание просто пропало. Стандарт ищи в описании диагностики: github.com/1c-syntax/bsl-language-server, `docs/diagnostics/<Код>.md`, строка «Стандарт: …» со ссылкой на its.1c.ru/db/v8std. Если ссылки на стандарт нет — так и скажи: это правило анализатора, а не стандарт.

Если в части 1 подключён сервер справки `1c-syntax`, методы и типы платформы сверяй по нему.

**Путь «Unica».** `unica.check` проверяет один адрес, а не папку: модуль обработки — `{"at": "main:ExternalDataProcessor.Обработка.Module.Object"}`, модули форм и общие модули — каждый своим адресом. Корень обработки и `Configuration` отвечают «passed» без проверки кода — это не проверка. В находке стандарта нет: открой `unica.docs` по ссылке `https://v8std.ru/diagnostics/bslls/<Код>/` с `"source": "development-standard"`; ответ `not_found` — скажи, что стандарта нет. Ответ `provider_unavailable` — это не «0 замечаний»: см. `guides/unica-windows.md`, раздел 6. Разбор замечаний — навык `/unica:code-diagnostics`. Исходное число замечаний по модулям `src\` запиши в `lint-baseline.txt` и закоммить; новых замечаний в твоём коде быть не должно. Модули `tests\` не считай: Unica не видит расширение YAxUnit и даёт на них ложные `UnresolvedMethodCall`. Методы платформы сверяй навыком `/unica:platform-help`; методы глобального контекста — `unica.docs` по имени с `"source": "platform-help"`, подпись из `snippet`, доступность так не узнать (гайд, разделы 6 и 7). После того как появились `src\` и `tests\`, `unica.check {}` должен дать `ready: true`.

**Путь «Своя связка».** Обёртка проверки кода из части 1, та же базовая линия в `lint-baseline.txt`.

**Готово, когда** (любой путь) исходное число замечаний закоммичено, а повторная проверка не показывает новых.

### Шаг 5. Сборка одной командой

```
pwsh -NoProfile -ExecutionPolicy Bypass -File .\build.ps1
```

**Готово, когда** код 0 и строка `Собрано: out\Обработка.epf`.

Если в журнале «Пользователь ИБ не идентифицирован» — неверный `v8User` или пароль, спроси человека. Если «Исключение XDTO» на форме — в сборочной базе другая конфигурация, спроси человека.

Код 0 у сборки не доказывает, что модуль цел: битый модуль конфигуратор при сборке обработки не ловит. Это покажет первый тест в шаге 6.

### Шаг 6. Тесты YAxUnit

YAxUnit — фреймворк модульных тестов для 1С, он стоит в базе как расширение. Тесты лежат в своём расширении `ТестыОбработки` (исходники в `tests\`), подключают собранный `.epf` и вызывают его методы.

**6.1. YAxUnit в копии.** Стоит с части 1, флажки сняты. Выгрузка для справки — `tmp\yaxunit`; если её нет, `.\dump.ps1 -Extension YAXUNIT -To tmp\yaxunit`.
**Готово, когда** есть `tmp\yaxunit\Configuration.xml`.

**6.2. Расширение с тестами.** Собери `tests\` по образцу выгрузки YAxUnit:

- скопируй `tmp\yaxunit\Configuration.xml` и папку `tmp\yaxunit\Languages\` в `tests\`;
- в `Configuration.xml`: имя `ТестыОбработки`, свой синоним и префикс имён; в составе оставь только языки, ссылки на объекты, которых в `tests\` нет (роли по умолчанию и прочее), убери;
- все идентификаторы в скопированных файлах замени новыми, кроме `ExtendedConfigurationObject` (это ссылка на объект основной конфигурации) и `ClassId` (это тип объекта);
- добавь общий модуль с тестами, например `ОМ_Обработка`, серверный: `tests\CommonModules\ОМ_Обработка.xml` и `tests\CommonModules\ОМ_Обработка\Ext\Module.bsl`, и впиши его в состав `Configuration.xml`.

В пути «Unica» навык `/unica:test-authoring` даёт только порядок работы, без кода (прогон 08.11): тесты пиши сам по образцу ниже, имена методов YAxUnit сверяй с `tmp\yaxunit`, как в любом пути. Запускает тесты `test.ps1`.

Первый тест — проба, что объект создаётся. Имена методов `ЮТТесты` и `ЮТест` сверь с выгрузкой YAxUnit, не по памяти:

```bsl
Процедура ИсполняемыеСценарии() Экспорт
	ЮТТесты.ДобавитьТест("ОбработкаСоздаётся");
КонецПроцедуры

// Битый модуль объекта сборка не ловит: его покажет только создание объекта.
Процедура ОбработкаСоздаётся() Экспорт
	ЮТест.ОжидаетЧто(Обработка() <> Неопределено).ЭтоИстина();
КонецПроцедуры

// test.ps1 кладёт собранный файл в каталог временных файлов под этим именем.
Функция Обработка()
	Возврат ВнешниеОбработки.Создать(КаталогВременныхФайлов() + "Обработка.epf", Истина);
КонецФункции
```

Дальше — тест на каждую функцию обработки: вызвать, сравнить с ожидаемым.

Затем `build-tests.ps1`. **Готово, когда** код 0.

**После первой загрузки — сразу к человеку.** Новое расширение `ТестыОбработки` встаёт с включёнными «Безопасный режим» и «Защита от опасных действий». Простые тесты пройдут, а тест, который пишет файл или открывает обработку не в безопасном режиме (`ВнешниеОбработки.Создать(..., Ложь)`), упадёт с «Установлен безопасный режим. Выполнение операции запрещено». Попроси человека снять оба флажка у `ТестыОбработки`: Конфигуратор → Конфигурация → Расширения конфигурации. Назови путь к базе из `baseCopy` и попроси сверить путь, а не название: у человека может быть несколько баз с одинаковым названием. Это один раз: при следующих загрузках `build-tests.ps1` флажки сохраняются. **Дождись ответа «сняты», только потом 6.3.** *Почему:* в повторном прогоне 07.11 флажки остались включёнными, клиент тестов встал без окна на экране и снялся только по тайм-ауту. Если две загрузки подряд не прошли — попроси человека создать в конфигураторе пустое расширение `ТестыОбработки` и выгрузи его: `.\dump.ps1 -Extension ТестыОбработки -To tests` (папка `tests\` должна быть пустой; если там твоя попытка, перенеси её в `tmp\`).

**6.3. Прогон.**

```
pwsh -NoProfile -ExecutionPolicy Bypass -File .\test.ps1
```

**Готово, когда** код 0, строка `ЗЕЛЁНЫЙ`, тестов больше нуля. Тогда коммит: `tests\` и правки `src\`.

Если не зелёный:

| Итог | Что делать |
|---|---|
| `Тестов: 0` или «нет итога» | Сверь имя расширения в `xUnitParams.json` с `tests\Configuration.xml`, есть ли `ИсполняемыеСценарии`, загружено ли расширение. Смотри `yaxunit.log` |
| «Файл не обнаружен …Обработка.epf» | Имя файла в тесте должно быть `Обработка.epf`, как в `test.ps1` |
| «Установлен безопасный режим. Выполнение операции запрещено» | Флажки у `ТестыОбработки` ещё не сняты (см. 6.2). Попроси человека снять «Безопасный режим» и «Защита от опасных действий» в Конфигураторе → Конфигурация → Расширения конфигурации |
| Код 3, тайм-аут или «клиент не дошёл до тестов» | Клиент ждал человека в модальном окне. Остановись. Попроси человека проверить в базе из `baseCopy` (по пути): у `YAXUNIT` и `ТестыОбработки` сняты «Безопасный режим» и «Защита от опасных действий», у пользователя снято «Предупреждать об опасных действиях»; для новых релизов типовых, которые на старой платформе показывают окно «Переход на новую версию платформы», нужна платформа, рекомендованная конфигурацией. После снятого прогона данные копии могли испортиться — попроси свежую копию |
| Красный тест | Причина в выводе. Правь код или тест, цикл заново |

### Шаг 7 (необязательный). Сценарные тесты форм в Vanessa Automation

Делай, только если в части 1 человек выбрал Vanessa, и в папке стенда есть `vanessa-automation-single.epf`, пустая база менеджера и сценарии. YAxUnit проверяет серверные функции, но не форму; Vanessa Automation в режиме тест-менеджера (`/TESTMANAGER`) открывает формы и нажимает кнопки, как пользователь.

```powershell
1cv8c ENTERPRISE /F mgr-base /N VA /TESTMANAGER /Execute vanessa-automation-single.epf `
  /C"StartFeaturePlayer;QuietInstallVanessaExt;DisableFirstRunHelper;VAParams=<VAParams.json>"
```

- `&` не ждёт и клиента 1С: запускай через `Start-Process -Wait` или с `| Out-Null` в конце строки.
- Итог бери из отчёта Vanessa в формате junit, а не из кода возврата.
- Пути в строке относительные: запускай из папки стенда.
- Менеджер работает в своей пустой базе, тестируемая форма открывается в копии. У пользователя менеджера должны быть сняты предупреждения об опасных действиях, иначе `/Execute` встанет на модальном окне.
- Окно «1С:Предприятие» с ошибкой после шага — дефект: исключение в коде формы или запроса.
- Сценарии идут минуты, запускай их, когда `lint.ps1` и `test.ps1` уже зелёные.
