# Правила для агента: внешняя обработка 1С с проверками

Этот файл читает ИИ-агент. Человеку — `README.md`.

Папка — проект одной внешней обработки. Ты правишь исходники в `src\`, собираешь их в копию базы одной командой, проверяешь код анализатором и тестами YAxUnit и по результату сам понимаешь, что сломал.

**С чего начать.** Настройка идёт по частям, по шагам и по порядку; каждый шаг кончается условием «Готово, когда».

- Нет `setup-log.md` или в нём нет строки `## Часть 1 — готово` — читай и выполняй `setup/1-machine.md`: опись машины, установка недостающего после «да» человека.
- Нет строки `## Часть 2 — готово` — `setup/2-project.md`: выгрузка, git, проверка кода, сборка, тесты до зелёного.
- Задача обращается к объектам конфигурации (справочники, документы, регистры, перечисления, общие модули), а строки `## Часть 3 — готово` нет — `setup/3-config.md`: выгрузка конфигурации базы, карта объектов, поиск по ним.
- Нужные части готовы — работай по «Рабочему циклу» ниже. Файлы `setup\` больше не читай.

## Главные правила

- Пиши человеку по-русски. Работай только в этой папке. Исключения: установка программ в части 1, и только туда, куда согласился человек; выгрузка конфигурации в каталоге `configDump` из `settings.json` (часть 3) — её читай и ищи по ней, а пишет в неё только `dump-config.ps1` (и твой скрипт индекса, если человек выбрал его в опроснике, — только в `index\`).
- 1С запускай только скриптами из корня папки: `install-ext.ps1`, `dump.ps1`, `dump-config.ps1`, `build.ps1`, `build-tests.ps1`, `lint.ps1`, `test.ps1`. Конфигуратор и клиент 1С напрямую не запускай; в пути «Unica» — ещё операции Unica по `guides/unica-windows.md`. *Почему:* в скриптах уже учтены ловушки (ожидание процесса, пользователь, кавычки, свежесть файлов), а свой вызов их потеряет.
- Скрипт запускай так: `pwsh -NoProfile -ExecutionPolicy Bypass -File .\build.ps1`. Если `pwsh` нет, вместо него `powershell`. *Почему:* скрипты из скачанного архива Windows без `Bypass` может не выполнить.
- В пути «Unica» её инструментами можно создавать и проверять метаданные и формы, выгружать и загружать расширения. Как вызывать, что работает и что нет — `guides/unica-windows.md`. Перед `pull`, `push` с `force`, `infobase.restore` и `push` с `delete` спроси человека: они без копии стирают правки или данные. Итог цикла всё равно дают только `lint.ps1`, `build.ps1`, `test.ps1`: Unica 0.13 не собирает `.epf` и не запускает тесты.
- **Имена — только из выгрузки.** Имена объектов конфигурации, их реквизитов, табличных частей, измерений, ресурсов, значений перечислений, общих модулей и их методов бери только найденные в выгрузке: карта `map.txt`, XML объектов, модули (`setup/3-config.md`, шаг 3.4). Не нашёл — спроси человека, похожее имя по памяти не подставляй. *Почему:* типовые конфигурации переименовывают объекты от релиза к релизу, а имя из памяти может быть из другой конфигурации. Ошибка в имени внутри текста запроса видна только при запуске теста.
- Конфигурацию и расширения базы не меняй. Выгрузку в `configDump` не правь и файлы в ней не удаляй: она общая для всех обработок по этой конфигурации.
- Скрипты набора не правь. Если скрипт сам ошибается, остановись и опиши человеку: команда, вывод, что ты ожидал.
- Ничего не ставь без «да» человека, только из официальных источников (часть 1).
- Работай только с копией базы из `baseCopy` в `settings.json`. Пути к базам и платформе в `settings.json` меняй только после «да» человека, другие базы не подставляй. Значения, которые назвал человек (путь, имя пользователя), пиши дословно, не сокращай и не «уточняй». *Почему:* тесты меняют данные базы.
- Не удаляй файлы. Свою неудачную правку откатывай через git.
- Про платформу 1С не утверждай того, чего не проверил запуском или справкой. Метод, которого нет в справке, не выдумывай. Сверяй по справке своего пути: сервер `1c-syntax` или навык Unica `platform-help`.
- Большие файлы (выгрузку YAxUnit в `tmp\`, чужие модули) читай кусками не больше 200 строк, нужное ищи поиском. *Почему:* иначе контекст забивается за минуты, и каждый следующий шаг стоит дороже.
- Одна и та же ошибка дважды — остановись и напиши человеку, что ему решить. *Почему:* без этого агент пробует одно и то же много раз, и человек платит за каждую попытку.
- Итог хода всегда на языке человека, и после остановки по ошибке тоже. *Почему:* в прогоне 09.11 агент после двух неудачных скачиваний написал итог по-английски, хотя весь разговор шёл по-русски.

## Как читать итог скриптов

Зелёный итог — только код выхода 0 **и** итоговая строка из таблицы. Любой другой код — не зелёный, даже если ошибок в выводе не видно.

| Скрипт | Зелёный | Не зелёный |
|---|---|---|
| `lint.ps1` | код 0, строка `Замечаний: N` | 1 — замечаний больше, чем в `lint-baseline.txt`; 2 — отчёта нет (это не «0 замечаний») |
| `build.ps1` | код 0, строка `Собрано: out\Обработка.epf` | 1 — файл не создан или старый, причина в журнале выше; 2 — нет исходников или `settings.json` |
| `build-tests.ps1` | код 0, строка `Расширение ТестыОбработки загружено` | 1 — ошибка загрузки или обновления базы |
| `test.ps1` | код 0, строка `ЗЕЛЁНЫЙ` и `Тестов: N` при N > 0 | 1 — красный тест (имя и причина в выводе); 2 — нет итога; 3 — тайм-аут: клиент не дошёл до тестов за 3 мин (нет `yaxunit.log`) или тесты не закончились за 10 мин |
| `dump.ps1` | код 0, строка `Выгружено` | 1 — ошибка выгрузки; 2 — неверные аргументы или файл уже есть |
| `install-ext.ps1` | код 0, строка `Расширение … установлено` | 1 — ошибка загрузки или обновления базы; 2 — неверные аргументы |
| `dump-config.ps1` | код 0, строки `Выгружено …` и `Карта: …` | 1 — ошибка выгрузки или карты; 2 — нет `configDump`, путь внутри проекта, чужие файлы в каталоге; 3 — тайм-аут, выгрузка неполная |
| `map-config.ps1` | код 0, строка `Карта: …` с числом объектов больше нуля | 1 — файл версий не читается; 2 — нет `configDump` или `ConfigDumpInfo.xml` |
| `inventory.ps1` | всегда 0: это опись, читай строки ЕСТЬ / НЕТ | — |

Если твоя среда обрывает команды по времени, дай `test.ps1` запас: 1С стартует десятки секунд, тесты идут минуты.

## Рабочий цикл

1. Правка кода в `src\`, тестов — в `tests\`.
2. Проверка кода по пути из `setup-log.md`: «Свои инструменты» — `lint.ps1`, «Unica» — `unica.check` по адресам модулей (см. `setup/2-project.md`, шаг 4), «Своя связка» — обёртка из части 1. Замечаний не больше, чем в `lint-baseline.txt`, а в строках `src\`, которые ты написал, ноль. На каждое новое замечание назови стандарт за ним и правь по стандарту (см. ниже). Ответ проверки «не удалось» (`provider_unavailable`, нет отчёта) — не ноль замечаний. Модули тестов в `tests\` не проверяются.
3. `build.ps1`.
4. Если менял `tests\`, то `build-tests.ps1`.
5. `test.ps1` до `ЗЕЛЁНЫЙ`. Красный тест — причину бери из вывода и `yaxunit.log`, не угадывай.
6. Проверь `git diff`: в нём только то, что нужно для задачи. Коммит с понятным сообщением.
7. Отчёт человеку: что сделано и итоговые строки проверки кода, `build.ps1`, `test.ps1` из вывода.

**Стандарт за каждым новым замечанием.** На каждое новое замечание анализатора назови человеку код диагностики и стандарт разработки 1С за ним и правь по стандарту, а не так, чтобы замечание просто пропало. Стандарт ищи в описании диагностики: github.com/1c-syntax/bsl-language-server, `docs/diagnostics/<Код>.md`, строка «Стандарт: …» со ссылкой на its.1c.ru/db/v8std. Если ссылки на стандарт нет — так и скажи: это правило анализатора, а не стандарт.

Новая функция — вместе с тестом на неё.

**Ожидаемое значение теста на данных базы — из независимого источника.** Возьми конкретные документы с их суммами или другой регистр (например, для реализаций — `РегистрНакопления.ВыручкаИСебестоимостьПродаж`), а не тот же запрос без группировки. *Почему:* ошибка в отборе, в выборе реквизита или в границах периода повторится и в ожидаемом значении, и тест останется зелёным. Так было в прогоне 09.11: тест проверял только группировку.

## Ловушки: правила и причины

Всё это уже учтено в скриптах. Записано здесь, чтобы ты не потерял это, если придётся разбираться вручную.

| Правило | Почему |
|---|---|
| Пустой результат — не зелёный. Нет `exitcode.txt` или `junit.xml`, ноль тестов, все пропущены — итога нет | Клиент без пользователя или не на том языке выходит молча с кодом 0. Пустое значение кода, приведённое к числу, тоже даёт 0, то есть «успех» |
| `1cv8.exe` из PowerShell — только с ожиданием: `Start-Process -Wait` или `& … \| Out-Null` | Это оконное приложение: оператор `&` его не ждёт, скрипт идёт дальше через доли секунды, журнала ещё нет, `$LASTEXITCODE` пустой |
| Всегда `/N` с пользователем, в кавычках | Без `/N` конфигуратор пишет «Пользователь ИБ не идентифицирован» и ничего не делает. `Start-Process` сам аргументы в кавычки не берёт |
| Клиенту — `/L ru` | Клиент 8.3.20 без него запустился по-английски, YAxUnit не нашёл ни одного теста и не записал журнал |
| Выгрузка обработки: первый аргумент — путь к корневому файлу `src\Обработка.xml`, не каталог | Каталог, которого ещё нет, конфигуратор принимает за имя корневого файла: рядом ляжет `src.xml`, а в `src\` — только формы и модули |
| Код 0 у сборки ничего не доказывает; первый тест — создание объекта | Конфигуратор не ловит битый модуль при сборке обработки |
| После сборки файл должен быть свежим | Иначе за результат сойдёт старый `.epf` от прошлого запуска |
| Расширение: `/LoadConfigFromFiles`, затем `/UpdateDBCfg` | Без обновления базы новый код не работает, хотя загрузка «прошла». Журнал у этих команд бывает пустым и при успехе: итог по коду возврата |
| Каталог отчёта BSL LS создаётся до запуска | BSL LS 1.0.7 его не создаёт, Java падает, а итог выглядел как «Замечаний: 0» |
| Для Java — UTF-8 | Иначе русские сообщения превращаются в кракозябры |
| Режим `all` в `bsl-ls.json` не выключается значением `false` у правила | Так на версии 1.0.7. Ненужное правило — меняй режим, а не отдельные значения |
| `test.ps1` работает из своей папки | Относительные пути в `xUnitParams.json` YAxUnit берёт от текущей папки, а не от JSON |
| Выгружай и собирай одной версией платформы | Формат выгрузки привязан к платформе; выгрузку более новой платформы старая может не прочитать |
| Сборочная база — с той же конфигурацией | Формы ссылаются на типы конфигурации, на пустой базе сборка падает с исключением XDTO |
| Только копия базы; после снятого посередине прогона — свежая копия | Тесты меняют данные: прогон, снятый посередине, оставляет данные, на которых следующий падает |
| Нет `yaxunit.log` через 3 минуты — клиент до тестов не дошёл | YAxUnit пишет журнал с первых секунд прогона. В повторном прогоне 07.11 клиент с невыключенными флажками безопасности стоял без окна на экране, и только тайм-аут его снял |
| Модальное окно — сразу к человеку | Клиент без человека ждёт без тайм-аута: «Предупреждение безопасности» при открытии файла, «Переход на новую версию платформы» |
| Файл версий, выгруженный отдельно (`-configDumpInfoOnly`), — в свой каталог `info\`, не в каталог полной выгрузки | Новый файл версий в каталоге выгрузки объявил бы её свежей, и следующее обновление (`-update`) пропустило бы настоящие изменения |
| Выгрузка конфигурации — вне папки проекта | В проекте её подхватили бы git и проверка кода; одна выгрузка нужна всем обработкам по этой конфигурации |
| Зелёные тесты на одной базе не проверяют ветки других конфигураций | Код под другую типовую на этой базе просто не выполняется |
