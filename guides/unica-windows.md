# Unica на Windows: установка, проверка всех операций, известные ошибки

Гайд читают агент и человек. В нём установка Unica в один проект, проверка, порядок прогона всех операций `unica.run` и таблица того, что работает, а что нет.

**На чём проверено (07–08.11.2026, два прогона и проверка обходов живыми вызовами):** плагин Unica 0.13.0 (адаптер `v8-runner` 0.14.0, анализатор `bsl-analyzer` 0.2.86), Claude Code 2.1.319, Windows 11, платформа 8.3.27.2342, файловая копия демобазы «Управление торговлей» 11.5.27.95 (2 ГБ). В другой версии Unica операции и ошибки могут отличаться: сверяйся со словарём `unica.run {}` своей версии.

**Источник:** github.com/IngvarConsulting/unica, лицензия LGPL-3.0-or-later. Поддерживается только платформа 8.3.27.x (README проекта).

## 1. Что нужно

- Git for Windows: сервер Unica стартует через `git` и `sh` из его состава.
- Платформа 1С 8.3.27.x.
- Claude Code или Codex. Ниже команды для Claude Code; на Codex прогон не делался, ставь по README проекта.
- Доступ к GitHub при первом вызове инструмента: рантайм (около 40 МБ) скачивается тогда, а не при установке. Пока он качается, `unica.run` отвечает `delivery_in_progress` — подожди и повтори.
- Права администратора не нужны.

## 2. Установка только в этот проект

Из папки проекта, после «да» человека:

```
claude plugin marketplace add IngvarConsulting/unica-marketplace --scope local
claude plugin install unica@unica --scope local
```

`--scope local` — единственное отличие от README. Без него обе команды пишут в настройки пользователя, и плагин попадает во все сессии агента на машине. С ним плагин включается записью в `.claude\settings.local.json` этой папки; глобальный `settings.json` не меняется. Сам плагин и рантайм всё равно лягут в общий кеш `%USERPROFILE%\.claude\plugins\` (около 55 МБ), но в других проектах он не включён.

**Цена в контексте:** плагин добавляет около 5–7 тыс. токенов в каждую сессию проекта: 5 тыс. по замеру 07.11, 7,3 тыс. по замеру 08.11 вместе с коннекторами аккаунта. В основном это список из 55 навыков с описаниями; схемы инструментов подгружаются по запросу.

Удалить:

```
claude plugin uninstall unica@unica --scope local
claude plugin marketplace remove unica
```

## 3. Проверка

1. Новая сессия агента в папке проекта.
2. `unica.run` с аргументом `{}`: ответ `ok: true` и словарь из 13 операций. 1С при этом не запускается.

**Готово, когда** словарь пришёл.

Как вызывать:
- `args` всегда объект, даже пустой: `{}`. Иначе ответ «run args must be an object».
- Долгая операция сразу отвечает `Task is still working` и `taskId`. Результат забирай `unica.task.result` (ожидание до 7000 мс за вызов) и повторяй, пока не придёт итог. Это не зависание. Если `unica.task.result` нет среди загруженных инструментов — загрузи его, а не объявляй, что операции висят.
- Операции в одном проекте — строго по одной. Два вызова сразу блокируют рабочую папку: второй ждал 451 с и получил `concurrent_change`.
- Журналы адаптера: `build\logs\` в папке проекта. Кириллица из ошибок `ibcmd` приходит в кодировке cp866.

## 4. Файлы проекта Unica

Пишутся вручную, отдельного инструмента нет. Подсказку со схемой даёт `unica.view {}` (поле `setup`). Так они выглядят в проекте внешней обработки набора (прогон 08.11):

`v8project.yaml` (в git):

```yaml
workPath: 'build'
format: DESIGNER
source-set:
  - name: main
    type: EXTERNAL_DATA_PROCESSORS
    path: 'src'
  - name: ТестыОбработки
    type: EXTENSION
    path: 'tests'
```

Для обработки набор `main` — типа `EXTERNAL_DATA_PROCESSORS`: с `CONFIGURATION` Unica обработку не видит. После этого `unica.view {}` отвечает `kind: external_processor`. Объект обработки должен называться так же, как корневой файл, то есть `Обработка`.

`v8project.local.yaml` (не в git):

```yaml
infobases:
  origin:
    connection: 'File=<каталог копии базы>'
    user: '<пользователь базы>'
tools:
  platform:
    version: '8.3.27.<сборка>'
    path: '<каталог bin платформы>'
    strict: true
```

- `user` задавай обязательно: без него `ibcmd` молча ждёт ввода и не завершается. Пароль не пиши в чат и в git; если он есть, его вписывает человек.
- `tools.platform` задавай обязательно и с `version`, и с `path`: без него справка `platform-help` берётся от другой установленной платформы (в проверках 08.11 — от 8.3.20 из `Program Files`), а без `path` справка недоступна вовсе (`not-configured`), хотя `unica.check {}` отвечает `ready: true`.

В `.gitignore` проекта добавь `build/`, `.build/`, `src/.build/`, `src/ConfigDumpInfo.xml`, `src/DumpFilesIndex.txt`, `tests/ConfigDumpInfo.xml`, `tests/DumpFilesIndex.txt`, `v8project.local.yaml`, `.claude/settings.local.json`, иначе `unica.check` даст `git.ignore_rule_missing`.

`.gitattributes` (этого требует проверка `repository.attributes`):

```
*.xml text eol=lf
*.bsl text eol=lf
```

После этого правь исходники инструментом правки файлов агента: замена через `sed` в Windows по таким файлам однажды молча не сработала.

Затем `git init` и коммит. `unica.check {}`: `repositoryReady: true` сразу, `ready: true` — когда есть `src\` и `tests\` (до этого — `source_set.path_missing`).

## 5. Порядок прогона всех операций

Операции `unica.run` проверялись 07.11 на проекте конфигурации (набор `main` типа `CONFIGURATION`, полная выгрузка УТ 11.5), а не на проекте обработки. Для обработки набора они не нужны: выгрузку, сборку и тесты делают скрипты набора.

Только на копии базы.

1. `unica.check {}` — ждём `ready: true`.
2. Каждую операцию сначала с `dryRun: true`, потом с `dryRun: false`. Предпросмотр работает для всех 13 операций без запуска 1С, за 1–1,5 с, и уже проверяет состояние: `push` без `pull`, `infobase.create` на существующей базе, `infobase.restore` без файла дают отказ в предпросмотре.
3. Читающие: `extensions.list`, `infobase.dump`, `download` со `state: "working"`.
4. `pull` с `force: true` — первый раз обязательно: до него `push` отказывает `no_memory`.
5. Меняющие: `push`, `make`, `extensions.set`, `infobase.restore`, `push` с `delete`, `infobase.create` (на отсутствующей базе).
6. `launch` — последним; через минуту проверь окна 1С: `Get-Process 1cv8* | Select-Object Name, MainWindowTitle`.

**Перед `pull`, `push` с `force: true`, `infobase.restore` с `mode: "replace"` и `push` с `delete` спроси человека.** Они без копии стирают локальные правки, данные базы или расширение с данными.

## 7. Путь Unica в наборе

Прогон 08.11: свежий агент по набору выбрал путь «Unica», поставил плагин и дошёл до зелёного `test.ps1` (5 тестов из 5). Версии: Unica 0.13.0, `bsl-analyzer` 0.2.86, `rlm-tools-bsl` 1.42.0, `v8-runner` 0.14.0.

| Задача | Чем в пути «Unica» | Работает | Как пользоваться |
|---|---|---|---|
| Проверка кода | `unica.check` по адресу модуля; разбор — `/unica:code-diagnostics` | частично | Анализатор настоящий: на модуле `ЗаказыСервер` УТ 11.5 25 из 32 находок совпали с BSL Language Server по месту. Адрес модуля обработки — `main:ExternalDataProcessor.Обработка.Module.Object`, модули форм и общие модули — каждый своим адресом; проверить все модули одним вызовом нельзя. До первой проверки доставь движок через `unica.search` (раздел 6) |
| Стандарт за замечанием | `unica.docs` со ссылкой `https://v8std.ru/diagnostics/bslls/<Код>/` и `source: "development-standard"` | да, где стандарт есть | В самой находке стандарта нет. Страница по ссылке даёт номер стандарта и ссылки its.1c.ru и v8std.ru; для части кодов стандарта нет (`not_found`) |
| Ревью изменения | `/unica:code-review` | да | Содержательные замечания со стандартами (два стандарта навык пометил «по памяти»); ложные `UnresolvedMethodCall` по YAxUnit |
| Справка платформы | `/unica:platform-help`; глобальный контекст — `unica.docs` по имени с `source: "platform-help"` | частично | Всё, что открылось, совпало со справкой 8.3.27.2342 из сервера справки. У методов глобального контекста — только подпись из `snippet`, без доступности (раздел 6). Без `tools.platform` с `path` — справка другой платформы или никакой |
| Черновик тестов YAxUnit | `/unica:test-authoring` | только порядок работы | Кода не даёт. Тесты пиши по образцу набора, имена YAxUnit сверяй с выгрузкой `tmp\yaxunit`; запуск — `test.ps1` |
| Новая внешняя обработка | `/unica:epf-init` | только порядок работы | Готового XML навык не даёт и на спецификацию не ссылается. Основной способ — шаблон набора `scripts\ExternalDataProcessor.xml`. Запасной — спецификация плагина `references/specs/1c-epf-spec.md` (лежит в папке плагина в `%USERPROFILE%\.claude\plugins`): по ней свежий агент сделал обработку, и `build.ps1` собрал её с первого раза (проверка 08.11). Сборка — `build.ps1` |
| Сборка `.epf` | нет | — | `build.ps1` (`make` собирает только `.cf`/`.cfe`) |
| Запуск тестов | нет | — | `test.ps1` (в 0.13 запуск тестов не опубликован) |

Сравнение проверки кода с BSL Language Server 1.0.7 на двух модулях УТ 11.5 (полная выгрузка конфигурации): у Unica 32 и 3 находки, у BSL LS 235 и 35 (127 и 18 без `UnknownMember`). Общие правила совпадают по месту. Только у Unica — устаревшие методы платформы, одинаковые выражения, неиспользуемые параметры, нет описания параметров. Только у BSL LS — стилевые правила (длина строки, пробелы, «магические» числа, опечатки), `UnknownMember`, парность транзакций. Unica считает строки с нуля.

## 8. Как это сочетается с набором

- Итог цикла по-прежнему дают `lint.ps1`, `build.ps1`, `test.ps1`: Unica 0.13 не собирает `.epf` и не запускает тесты.
- Операции Unica и скрипты набора запускай по очереди, не одновременно: и те и другие работают с той же копией базы, а две операции Unica сразу уже блокируют друг друга (раздел 3).
